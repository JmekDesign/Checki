# Checki — Рабочий процесс с Claude Code

Этот документ описывает, как работать с проектом через Claude Code агентов.
Написан для тех, кто не является профессиональным разработчиком.

---

## 1. Как запустить Claude Code

1. Подключиться к серверу по SSH:
   ```
   ssh ilya@<адрес-сервера>
   ```

2. Перейти в папку проекта:
   ```
   cd /home/ilya/projects/cheks/checki
   ```

3. Запустить Claude Code:
   ```
   claude
   ```

После запуска можно описывать задачу прямо в терминале.

## 2. Как описывать задачу

Хорошее описание содержит: **что сделать**, **где** (экран/эндпоинт/файл), **почему** или **какой результат ожидается**.

### Примеры плохих описаний

> "Поправь чеки"

Непонятно что именно, в каком месте, что считать исправленным.

> "Сделай красиво"

Нет конкретики. Агент не знает ваших предпочтений.

> "Что-то сломалось при закрытии"

Нет воспроизведения, нет симптомов.

### Примеры хороших описаний

> "При закрытии чека поле `total` не обновляется — в базе остаётся 0. Починить расчёт в роутере `checks_close`."

> "Добавь эндпоинт `GET /api/checks/{id}/receipt` — возвращает чек с позициями и итогом, для страницы печати."

> "На странице архива чеков добавь фильтр по сотруднику (dropdown со списком пользователей заведения)."

**Правило:** если можете сказать, в каком файле или на каком экране проблема — скажите. Это сильно ускоряет работу агента.

## 3. Pipeline разработки

В зависимости от сложности задачи используется разный набор агентов.

### Маленькие задачи

Баг-фикс, небольшое изменение только на фронте, правка текста, добавление валидации.

```
Описание задачи → implementer → готово
```

Примеры: опечатка, кнопка не работает, неправильный текст ошибки.

### Средние задачи

Новый эндпоинт, изменение логики существующего роутера, новый экран на фронте.

```
Описание задачи → designer (проектирует) → вы проверяете дизайн → implementer → reviewer
```

Примеры: новая страница, изменение формата ответа API, добавление поля в форму.

### Сложные задачи

Изменения в нескольких модулях одновременно, финансовая логика, вопросы изоляции данных между заведениями.

```
Описание задачи → designer → вы проверяете → implementer-senior → reviewer → tester
```

Примеры: добавление новой роли пользователя, изменение схемы БД, логика расчёта итогов чека.

## 4. Проверки перед коммитом

Перед сохранением изменений в git всегда запускайте три команды:

```bash
make test && make lint && make typecheck
```

Расшифровка:
- `make test` — запускает автотесты (проверяет, что ничего не сломалось)
- `make lint` — проверяет стиль кода
- `make typecheck` — проверяет типы (ловит скрытые баги)

Все три должны завершиться без ошибок. Если что-то упало — сообщите агенту вывод команды.

Pre-commit хук (`pre-commit install`) запускает эти проверки автоматически при каждом `git commit`.

## 5. Примеры промптов

Скопируйте подходящий пример и адаптируйте под свою задачу.

**Новый эндпоинт:**
```
Добавь эндпоинт GET /api/checks/{id}/receipt — вернуть чек с позициями и итогами для страницы печати.
```

**Фильтр в архиве:**
```
В архиве чеков добавь фильтр по сотруднику: dropdown с именами пользователей текущего заведения.
```

**Баг-фикс:**
```
Поправь баг: при закрытии чека поле total не пересчитывается, остаётся 0 в базе.
```

**Новая страница:**
```
Добавь страницу управления гостями: список гостей заведения с именем и количеством визитов.
```

**Изменение валидации:**
```
При добавлении позиции в чек — запретить qty = 0 или отрицательное. Вернуть HTTP 422 с понятным сообщением.
```

## 6. Когда звать implementer-senior

Используйте `implementer-senior` (модель opus) вместо обычного `implementer` в случаях:

- **Cross-module изменения** — задача затрагивает несколько роутеров или модулей одновременно
- **Финансовая логика** — всё, что касается `price_snapshot`, `line_total`, `total` в чеках
- **Изоляция заведений** — любые вопросы про `venue_id`, мультитенантность, доступ к данным
- **Изменение схемы БД** — добавление/изменение таблиц или столбцов (требует файл миграции в `sql/`)
- **Неочевидные бизнес-правила** — когда вы не уверены, как должно работать по-правильному
- **Новые роли пользователей** — изменения в auth/permissions

Если сомневаетесь — берите senior. Лучше потратить чуть больше времени, чем получить незаметный баг в финансах.

## Справочник агентов

| Агент              | Когда использовать                              |
|--------------------|------------------------------------------------|
| designer           | Проектирование — до написания кода             |
| implementer        | Обычные задачи: баги, CRUD, фронт              |
| implementer-senior | Сложные задачи (см. раздел 6)                  |
| reviewer           | Проверка кода после implementer                |
| tester             | Написание тестов                               |
